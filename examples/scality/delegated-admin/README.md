# Delegated administration example

A management account manages the buckets and IAM of several sub-accounts
through [`delegated-admin-role`](../../../modules/scality/delegated-admin-role).
It doesn't need the sub-accounts' keys, and there's no operator user inside
them.

```
superadmin     -> mgmt account, customer-a, customer-b          (bootstrap)
mgmt root      -> delegator user (sts:AssumeRole on the roles)  (bootstrap)
sub-acct root  -> account-manager role, trusting delegator      (bootstrap)
delegator      -> assumes each role -> bucket + user per sub    (managed)
```

There are two root configs, applied in order. A role has to exist before a
provider can be configured to assume it, so the two stages can't share one
apply.

| Directory | Credentials | Creates |
|---|---|---|
| [`bootstrap/`](bootstrap) | Superadmin (env), then each account's root keys | Accounts, the `delegator` user, one role per sub-account |
| [`managed/`](managed) | `delegator`'s keys + `assume_role`, one provider alias per sub-account | A bucket and an `app` user in each sub-account |

## Run

```sh
export SCALITY_ENDPOINT=http://your-cluster:8080
export SCALITY_ACCESS_KEY=...   # superadmin, used only by bootstrap
export SCALITY_SECRET_KEY=...

# 1. Bootstrap
cd bootstrap
tofu init
tofu apply

# 2. Hand the outputs to the managed stage through env vars (no files)
export TF_VAR_delegator_access_key="$(tofu output -raw delegator_access_key)"
export TF_VAR_delegator_secret_key="$(tofu output -raw delegator_secret_key)"
export TF_VAR_role_arns="$(tofu output -json role_arns)"

# 3. Managed
cd ../managed
tofu init
tofu apply
```

Tear down in reverse. The accounts can't be deleted while they still hold
buckets or users.

```sh
cd managed && tofu destroy
cd ../bootstrap && tofu destroy
```

Set `TF_VAR_name_prefix` to the same value for both stages to keep repeat
runs from colliding.

## Adding a sub-account

1. Add it to `sub_accounts` in the bootstrap and apply. This creates the
   account and its role, and extends `delegator`'s `sts:AssumeRole` policy.
2. Add a `provider "scality"` block for it in `managed/provider.tf`, plus its
   resources.

Terraform doesn't support `for_each` on provider blocks, so each
sub-account's provider is declared explicitly, or generated by tooling such
as Terragrunt.

## What an apply checks

- The management user, created by `application-identity` with an
  `sts:AssumeRole` policy, can assume a role in a different account.
- Resources created without per-resource credentials land in the
  sub-account. The `app_user_arns` output carries each sub-account's ID.
- Destroy runs cleanly in reverse order.

## Security notes

- The bootstrap state holds every account's root keys and `delegator`'s
  secret key. Protect it, and move the root keys into a secret store if you
  have one.
- After a compromise of `delegator`, change `delegator_username` and
  re-apply the bootstrap. Recreating the user with the *same* name gets it
  the same access back. See the module's caveats.
